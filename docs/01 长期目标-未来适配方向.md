## 〇、长期目标（总纲）

**一句话目标：把所有"本该直连官方 1mao（内置模型/权益/平台）"的请求，改道到 localTool 统一转发，由 localTool 决定实际转发给谁（官方 / Lovart / 其他 API / 本地兜底）。**

### 为什么
官方 1mao 闭源，账号/权益/会员判定 100% 在官方远程。当前前端这些请求**直连官方**（base 默认取官方候选地址，`docs/20` §7.1 实测），导致：
- 散乱裸连官方、来源判定混乱、无降级兜底；
- 本地自托管时仍依赖官方模型/权益（本地不可用）。

### 目标架构
```
前端【全部】请求
   │  改 src/bundle 后 base → 127.0.0.1:18080（npm run build 回灌 dist/）
   ▼
localTool（唯一出口网关，决定发给谁）
   ├─ 命中本地路由 ─┬─→ 本地处理（文件/任务/资源/KV）
   │                ├─→ Lovart / apimart-gateway
   │                ├─→ 其他 API / 网站（x-official-base / KV 覆盖）
   │                └─→ 本地静态清单兜底（内置模型，不依赖官方）
   └─ 未命中 ────────→ catch-all 兜底透传 → 官方 1mao（原样回传）
```

### 核心原则（2026-08-01 确立）
**不区分"该不该直连官方"—— 全部走 localTool。即使最终目的地仍是官方，也必须经 localTool 转发。**
localTool 从"白名单路由服务"升级为"唯一出口网关"，未接管的请求由 catch-all 透传，而非 404。
⇒ 由此派生一条**硬前置**：改 base 之前，必须先给 localTool 补 catch-all 兜底透传（详见 `docs/21` §六）。

### 落地方式：改 src/bundle，让前端 base 指向 18080
前端这些请求的 base 经 `g()`(u()||l()) 链默认取官方地址，且 `g()` 只读 sessionStorage、不读 KV——所以**必须改 `src/bundle/`**（把 base 指向 `http://127.0.0.1:18080` 后 `npm run build` 回灌 `dist/`）才能让请求走 localTool。这是方向一、五、六的**同一套 base 改造**。

### 各方向定位
| 方向 | 归属 | 一句话 |
|---|---|---|
| 一 官方权益转发层 | 改 src/bundle | 权益/会员请求走 localTool 转发官方（+缓存降级） |
| 二 特惠视频第三方 | 改 src/bundle | 特惠节点复用"选 apiConfig"机制；**若全面自研接管，"特惠"概念本身消解**（见方向二前提辨析） |
| 五 内置模型平台接口 | 改 src/bundle | 模型清单请求走 localTool，显示本地静态模型（不再直连官方） |
| 六 A1 画布助手 | 改 src/bundle | 助手 `/agent/*` 走 localTool/本地，不裸连官方 |
| 三 剪映发送 | localTool 补能力 | 发剪映功能 stub，待实现 |
| 四 工作流应用市场 | localTool 补能力 | 应用市场返回 stub，待实现 |

## 一、官方权益接口转发层（未实现；仅 localTool 后端就绪，前端未改）

### 背景（现状）
官方 1mao 闭源，账号/权益/会员判定 100% 在官方远程服务器。自研链（localTool → apimart-gateway → Lovart）已承接生图/生视/聊天，但**账号/权益类接口仍散乱直连官方**。`docs/20` 提出在 localTool 加"官方权益接口转发层"，统一入口 + 中转 + 短缓存。

### localTool 后端已实现（🟡 仅供后续接管；前端 base 未改，整体未落地）
- `localTool/src/routes/official.ts` 新增四个端点：
  - `GET /api/user/info` → 官方 `/user/info`（内存缓存 60s）
  - `GET /api/user/model-entitlements` → 官方 `/user/model-entitlements`（内存缓存 300s）
  - `GET /api/agent/:id/vip-check` → 官方 `/agent/:id/vip-check`（实时透传，不缓存）
  - `POST /api/official/entitlements/invalidate` → 主动失效缓存
- 透传 Bearer、错误透传官方原始状态码/body、降级 stale（`x-cache: hit-stale`）不伪造 `allowed:true`、日志 `[official]` 前缀脱敏。
- `index.ts` 注册路由；`CLAUDE.md` 职责补为八类（新增第 8 类）。

### ⚠️ 实测结论（dist 混淆源码逐字反查，2026-08-01）
- 前端三处权益接口的 base **不是**"默认即 18080/localTool"，而是经 `g()`(u()||l()) 链默认取候选列表 `s()[0]`（官方地址 `https://www.1mao.cc`）。
- 且 `g()` **只读 sessionStorage、不读 KV** → `docs/20` §3.3 的"KV 重定向让 JSON 落 localTool"对这三处**无效**。

### 未实现（需前端改 src/bundle，才能让转发层真正生效）
现状：前端三处请求仍直连官方候选地址，**不经过 localTool 18080**，本地转发层处于"就绪但未被调用"。要让请求打到这里，需改 `src/bundle/` 把三处 base 指向 `http://127.0.0.1:18080` 后 `npm run build` 回灌 `dist/`：

| 前端调用 | 混淆变量/位置（src/bundle） | 改法 |
|---|---|---|
| `/user/info` | `ut("/user/info")`、`_t.get("/user/info")`（App，`gn as ut` / `i as _t`） | base 改指 `http://127.0.0.1:18080` |
| `/user/model-entitlements` | `Ui(e2,...)` 首参 `e2`（httpClient） | base 改指 `http://127.0.0.1:18080` |
| `/agent/{id}/vip-check` | `fetch(`${Je}${st}/agent/...`)`（App，`Je = Wn = Nn()`） | base `Je` 改指 `http://127.0.0.1:18080` |

> 前置：按 CLAUDE.md §四.5 规范改 `src/bundle/` 并登记变更；build 后验证三请求落 18080 且官方不可达时走 stale 缓存（`x-cache: hit-stale`）。
> 替代路径（免改 src）：用户在画布 UI 把接入点切到 localTool/18080（写 sessionStorage）——依赖手动切换，非默认态。

## 二、特惠视频（discountVideo）支持第三方 API（待改 src/bundle）

### 背景（现状）
特惠视频节点**只支持内置模型、不支持第三方 API**，是**设计上的硬隔离**（非 Bug），根因是特惠节点整条链路与 `apiConfigs` 下拉**解耦**（详见 `docs/16`）：

| 维度 | 普通视频/图节点 | 特惠视频节点（discountVideo） |
|---|---|---|
| 模型下拉数据源 | `apiConfigs` 合并后的模型清单 | 硬编码字段 `discountVideoModel`（`\n` 拆分的纯文本） |
| API 地址 | 选中 apiConfig 的 `e3.apiUrl` | 固定字段 `discountVideoApiUrl`（闭包常量 `u2`） |
| 鉴权头 | 选中 apiConfig 的 `e3.apiKey` | 固定字段 `discountVideoApiKey`（闭包常量 `d2`） |
| 是否可切换 API 配置 | 是（内置+自建都出现，内置排前） | 否（面板无下拉入口） |

### 未来方向：改 src/bundle，让特惠视频复用"选中 apiConfig → url/key"机制
目标：特惠节点也能选第三方 API。**奥卡姆剃刀最小改动**（`docs/16` §6.7/6.8）只需打通"上游来源"这一处断点，下游零改动：

1. **把特惠的 `u2`/`d2` 改为由 `apiConfigs.find(选中ID)` 驱动**——与其他节点完全一致：
   - 给特惠面板复用普通节点的"API 配置"下拉组件（已存在，只是没挂到特惠面板）。
   - 选中后执行同款 `Y.find(e4=>e4.id===选中ID)` → 取 `.url` 赋 `u2`、`.key` 赋 `d2`。
   - **不动**下游消费 `m3=${(u2||"")...}/v1/gateway/task/...` 与 `Bearer ${d2}`——只换上游来源，改动面最小。
2. **模型下拉同步复用**：数据源从硬编码 `discountVideoModel`（`Ur`）切到"选中 apiConfig 的模型清单"，与普通节点共用同一渲染分支。

### 前提与风险（务必业务确认）
- **计费/额度隔离（关键）**：特惠视频有专属定价与额度，原设计把 url/key 锁死就是为了强制走特惠计费通道。放开第三方会**绕过特惠计费**，造成财务漏洞。建议采用白名单（`allowInDiscount` 标记），仅允许显式勾选的第三方进入特惠，而非全部开放（`docs/16` §6.2 方案 A > 方案 B、§6.4）。
- **路径模板兼容**：普通节点拼 `/v1/gateway/task/...` 后缀。若第三方基址不同，需在 apiConfig 上存完整基址或约定"进入特惠的第三方 `apiUrl` 为兼容 `/v1/gateway/task` 的网关地址"，避免改调用代码（`docs/16` §6.7 注意）。
- **响应结构兼容**：第三方接口的轮询状态码（`e4===3/"success"/"completed"`）可能与特惠链路不一致，需做响应适配。

### ⚠️ 重要前提辨析（2026-08-01 补）：自研接管后「特惠」概念消解
「特惠视频」的本质**不是一种技术能力，而是官方的一套商业定价通道**——官方用锁死的 `discountVideoApiUrl` / `discountVideoApiKey` / `discountVideoModel` 把请求强制打到自己的特惠计费网关，从而给出低于常规的价格。

因此，一旦按〇总纲把模型改走**我们自己的 API**（localTool → apimart-gateway → Lovart / 第三方）：

- **计费主体变了**：账单由我们的上游供应商结算，官方特惠价不再适用；
- **「特惠 vs 普通」的区分失去意义**：两者都只是"选一个 apiConfig 发一个视频任务"，差别仅剩模型名与单价，不再有独立通道；
- **特惠节点本身沦为冗余**：它与普通视频节点的唯一差异（锁死的 url/key/模型）已被移除。

所以本方向存在两条互斥路线，需先做**业务决策**：

| 路线 | 做法 | 适用前提 |
|---|---|---|
| **A. 保留官方特惠** | 不动 `u2`/`d2`，特惠节点继续直连官方特惠通道；只放开"白名单第三方"作为补充 | 仍要吃官方特惠价，接受账号/权益依赖官方 |
| **B. 自研接管（推荐，与〇总纲一致）** | 特惠节点与普通视频节点**合并**，统一走 apiConfig 选择；不再保留"特惠"字样，或降级为一个普通的低价模型选项 | 已全面走自研链，不再依赖官方计费 |

> 结论：若走路线 B，则本方向的"让特惠支持第三方"实际等价于**删除特惠节点的特殊性**——不是加功能，而是**做减法**。下方"复用 apiConfig 机制"的改造方案，正是路线 B 的最小实现路径；路线 A 才需要额外做白名单与计费隔离。

### 落地入口
改点在 `src/bundle/` 前端源码（对应 `App-BX6o9fW5.js` / `httpClient-BknZwXjG.js` 中的 `u2`/`d2`/`Ur`/`apiConfigs` 合并数组 `a3`），在 `src/bundle/` 实现后 `npm run build` 回灌 `dist/` 验证。
